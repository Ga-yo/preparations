# M5: 5단계 비교·구매 결정 + 정비사업 데이터 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 관심 단지 2~4개를 결정론적 비교 표(가격·예산 대비·적합도·단지 지표·위험 요소·정비사업 단계)로 나란히 보여주고, 직전 조건 대비 후보 변화와 구매 전 확인 사항·다음 절차를 안내한다. DeepSeek(`deepseek-v4-pro`)는 같은 결과를 툴로 받아 해석만 한다.

**Architecture:** 로드맵의 M5(5단계)와 M6(정비사업)을 한 마일스톤으로 합치고, M4처럼 PR 두 개로 나눈다. **M5a**는 새 데이터 없이 기존 `loadConditionContext`·`rankComplexes`·`fitScore` 위에 순수 함수 `lib/calc/compare.ts`·`lib/calc/scenario.ts`와 툴 2개, 5단계 화면을 올린다. **M5b**는 서울 정비사업 구역 CSV를 커밋해 `redevelopment_projects`(M1 스키마에 이미 있음)에 적재하고 단지와 매칭해 비교 표·4단계 상세에 붙인다. M5b는 실제 파일을 받아 컬럼·매칭률을 확인하는 Task 6의 관문을 통과해야 진행한다.

**Tech Stack:** M4와 동일. Next.js 16 App Router, zod v4, vitest, Supabase CLI(로컬)·pgTAP, collector(uv, pytest). M5b만 collector·워크플로를 바꾼다.

**Spec:** `CLAUDE.md`("5단계. 조건 조정 및 구매 의사결정", "4단계 ③ 주변 개발 및 정비사업 정보", 원칙 1~11), 로드맵 `2026-11-03-roadmap.md`의 M5·M6. 2026-11-13 대화에서 사용자가 M5·M6 통합과 DeepSeek 비교 분석을 결정했다.

**선행 조건:** PR #6(M4b) 머지 + 원격 `supabase db push` 완료. 그 뒤 `main`에서 `feat/m5-decision` 브랜치. M5a는 새 키가 필요 없다. M5b는 서울 열린데이터광장 파일 다운로드만 하고 키는 쓰지 않는다.

## Global Constraints

- 모델 ID: 5단계 `deepseek-v4-pro`(기존 `modelForStage`). `deepseek-chat`·`deepseek-reasoner` 금지.
- 금액·비율·순위·차이는 `lib/calc` 또는 SQL로만 계산한다. LLM은 툴 숫자와 코드만 인용한다.
- 에이전트·웹은 공공 API를 실시간 호출하지 않는다(K-apt 관리비 예외는 단지 상세에만). 툴 결과 `as_of`에 쓴 데이터셋 기준일을 모두 넣는다(M5b는 `redevelopment:seoul` 등 Task 6에서 정한 이름).
- 툴 인자는 1단 스키마, zod 검증(`defineTool`이 강제). `complex_ids`는 양의 정수 배열(원시값 배열은 허용).
- 지역 코드는 저장된 `condition_sets.region_codes`·`complexes.region_code`·`regions`에서만 나온다. 정비구역의 법정동 코드도 collector 코드가 주소로부터 `regions`에서 찾는다(LLM 금지).
- 실거래 집계 규칙(M2~M4 동일): `cancel_date is null`, `deal_type is distinct from '직거래'`, KST 기간.
- 스키마 변경은 `supabase/migrations/*.sql`, 새 함수는 `set search_path = ''`, security invoker. 새 사용자 테이블은 없다.
- LLM에 소득·자산 원값을 보내지 않는다. 예산은 `max_budget`(계산 결과)과 비율만 보낸다.
- 투자 권유나 "오른다/반드시" 같은 단정 표현은 TIP·프롬프트·화면 문구 어디에도 쓰지 않는다. 정비사업 단계는 "진행 중인 절차"로만 말하고 사업성·시세 영향은 단정하지 않는다.
- 단위: 면적 ㎡, 금액 원, 날짜 KST `YYYY-MM-DD`.
- Next.js 16 코드를 쓰기 전에 `apps/web/node_modules/next/dist/docs/01-app/`의 searchParams·Server Actions 문서를 읽는다.
- 로컬 실행·테스트는 메모리 규칙대로 한다: `.env.local` 수정·출력 금지, 로컬 Supabase `http://[::1]:54321`, env는 명령에 직접 넣는다.
- collector에서 키가 URL에 들어가는 호출은 없다(M5b는 파일 적재). 워크플로 액션은 SHA 고정, secrets는 run 단계 env에만.

## Review Focus

1. **관심 단지가 0~1개** — 비교 화면은 빈 표가 아니라 "4단계에서 관심 단지를 2개 이상 저장하세요"와 링크를 보여주고, 툴은 `{ error: "need_two_or_more" }`를 돌려준다. (Task 2 `need_two_or_more`, Task 5 화면)
2. **URL ids 조작**(중복, 5개 이상, 0·음수·문자, 관심 단지가 아닌 id) — 중복은 제거하고, 관심 단지가 아닌 id는 무시하고, 남은 게 2개 미만이면 1번과 같이 처리한다. 500이 나면 안 된다. (Task 5 `parseIds`)
3. **조건을 바꾼 뒤 예전 관심 단지**(현재 지역·면적 밖) — 비교에서 빠지지 않는다. `fit: null`, 위험 코드 `outside_conditions`. (Task 1 `outside conditions has null fit`, Task 2)
4. **조건 세트가 하나뿐**(직전 행 없음) — 오류가 아니라 "조건을 바꿔 저장하면 변화를 보여줍니다". (Task 3 `no_previous_conditions`)
5. **(M5b) 동명 단지, 데이터 없는 시·도** — 다른 법정동의 같은 이름 단지에는 붙이지 않는다. 경기·인천 단지는 "정비사업 없음"이 아니라 "정비사업 데이터 미제공 지역"으로 나온다. (Task 7 `same name other dong not matched`, Task 9 `not_covered outside seoul`)

## M5a — 5단계 비교 (기존 데이터)

### Task 1: `lib/calc/compare.ts` — 비교 표와 위험 요소

**Files:** Create `apps/web/lib/calc/compare.ts`, `compare.test.ts`

**Interfaces:**
- Consumes: `ComplexRow`, `Fit`(`lib/calc/fit.ts`).
- Produces:
```ts
export type RiskCode = "over_budget" | "budget_unknown" | "few_trades" | "no_recent_trades"
  | "old_building" | "no_location" | "outside_conditions" | "redevelopment_in_zone";
export type Metric = "median_price" | "fit_score" | "approval_year" | "household_count"
  | "parking_per_household" | "land_share_m2" | "nearest_station_m" | "nearest_elementary_m";
export interface CompareInput { row: ComplexRow; fit: Fit | null; max_budget: number | null; in_conditions: boolean }
export interface CompareItem {
  complex_id: number; name: string; fit: Fit | null; risks: RiskCode[];
  price_gap_from_min: number | null;  // median_price - 비교 대상 중 최저 median_price
  budget_ratio: number | null;        // median_price / max_budget, 소수 둘째 자리
}
export interface CompareResult { items: CompareItem[]; best: Partial<Record<Metric, number[]>> } // 지표별 최선 complex_id(동률 모두)
export function riskFlags(x: CompareInput, todayYear: number): RiskCode[];
export function compareComplexes(inputs: CompareInput[], todayYear: number): CompareResult;
```
- 최선 방향: `median_price`·`nearest_*`는 작을수록, 나머지는 클수록 좋다. 값이 null인 단지는 최선 후보에서 빠진다. null이 아닌 값이 1개 이하인 지표는 `best`에 넣지 않는다.
- `old_building`: `approval_year !== null && todayYear - approval_year >= 30`. `few_trades`: `deal_count` 1~2, `no_recent_trades`: 0. `outside_conditions`: `!in_conditions`. `redevelopment_in_zone`은 Task 9에서 호출자가 붙인다(이 함수는 내지 않는다).

- [ ] **Step 1: 실패하는 테스트** — `compare.test.ts`:
  - `price gap and budget ratio` — 중위가 [5억, 6억], 예산 5.5억 → gap [0, 1억], ratio [0.91, 1.09], 두 번째에 `over_budget`.
  - `best picks lowest price and newest year` — 동률이면 두 id 모두.
  - `null values excluded from best` — 한 단지 `household_count: null` → best에 다른 단지만. 다른 단지도 null이면 `best.household_count` 없음.

- [ ] **Step 2: 실패 확인** — Run: `pnpm --filter web test compare` / Expected: FAIL(모듈 없음).
- [ ] **Step 3: 구현** — 위 인터페이스대로. `fit_score` 지표 값은 `fit?.score ?? null`.
