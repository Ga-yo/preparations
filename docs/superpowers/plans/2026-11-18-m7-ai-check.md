# M7 — 단계별 AI 점검 (에이전트가 먼저 짚어 주기)

**작성일:** 2026-11-18 · **상태:** 구현 완료(2026-11-18, 미커밋) · **브랜치:** feat/m7-ai-check

## 배경과 목표

지금 AI는 채팅에서 물을 때만 움직이고, 무엇을 확인했는지 화면에 남지 않는다. 5단계 흐름은 AI 없이 끝까지 돈다.
"AI 에이전트답다"의 기준(2026-11-18 논의):
1. 부동산을 모르는 사용자: 물어볼 줄 몰랐던 것을 먼저 짚어 주는가
2. 평가자·발표 청중: AI가 스스로 툴을 골라 여러 번 부르고 결론 내는 과정이 보이는가

사용자 결정: **B안(단계별 AI 점검)** + 아래 5가지 추가, 실행은 **"AI 점검 받기" 버튼**.

## 결정 사항

| # | 결정 | 근거 |
|---|------|------|
| M7-D1 | 각 단계 채팅 패널 위에 "AI 점검 받기" 버튼. 누르면 에이전트가 단계 목표를 받아 툴을 스스로 골라 최대 5스텝 실행하고 브리핑을 낸다. | 사용자 결정(자동 대신 버튼: 한도 절약) |
| M7-D2 | 브리핑 아래 "AI가 확인한 것: 예산 계산 → 조건 점검 → …"(호출한 툴 이름의 한글 라벨) 표시. | 기준 2 |
| M7-D3 | 추천 질문: 점검 응답에 질문 2~3개를 함께 받아 **칩**(누르면 바로 전송)과 입력창 placeholder로 보여 준다. 점검 전·실패 시에는 **입력값 규칙으로 고른 기본 질문**(`lib/agent/suggestions.ts`, 순수 함수)을 보여 준다. 추가 Gemini 호출 없음. | 사용자 제안 + 무료 한도 |
| M7-D4 | 단계 간 기억: 앞 단계들의 최신 점검 요약을 다음 단계 점검 입력에 넣는다. | B 추가안 1 |
| M7-D5 | 제안은 AI, 저장은 사용자: 점검이 3단계 우선순위 변경(`priority.<key>` → `prefer`/`ignore`)을 제안하면 "이 조건 바꿔 보기" 링크로 3단계 폼 라디오만 미리 선택해 둔다(`?prefill=`). 저장은 사용자가 누른다. 허용 키는 `PRIORITY_KEYS`, 값은 zod로 검증. | B 추가안 2, AI가 사용자 데이터를 직접 쓰지 않음 |
| M7-D6 | 데이터 기준일·stale은 점검 프롬프트에서 먼저 짚게 한다(툴 결과에 이미 있음). | B 추가안 3 |
| M7-D7 | 5단계 점검 = 리포트 AI 해설: 리포트를 만들 때 **현재 입력과 같은 입력으로 만든** 최신 5단계 점검 요약을 `reports.narrative`에 복사. M6b의 별도 해설 버튼(`generateNarrative`, `lib/report/narrative.ts`)은 지운다. | B 추가안 4, 같은 일을 두 번 만들지 않음 |
| M7-D8 | 채팅 기록 유지: 새로고침해도 `chat_messages`의 최근 user/assistant 20개를 다시 보여 준다. | B 추가안 5, DB엔 이미 저장 중 |
| M7-D9 | 캐시: 입력 해시(재무 프로필 + 최신 조건 + 관심 단지 + 오늘 날짜(KST))가 같고 같은 단계 점검이 있으면 Gemini를 부르지 않고 그 결과를 보여 준다. 점검 1회는 채팅 하루 한도(`bump_chat_usage`) 1회로 센다. | 원칙 11 |
| M7-D10 | 점검도 채팅과 같은 숫자 규칙(툴 결과에서만 인용, `SYSTEM_PROMPT`)을 쓴다. 지역 선호 이유(`region_reason`)는 어떤 툴도 돌려주지 않으므로 LLM에 가지 않는다. | 원칙 1·9 |

## 하지 않는 것

- 저장 시 자동 점검(버튼으로 결정), 3단계 우선순위 외 값 미리 채우기(가격·면적 등), 점검 결과 스트리밍.
- 채팅 응답에 툴 흔적 표시(점검에만).

## 데이터 (원칙 6·7·11)

`supabase/migrations/20261118000000_m7_ai_checks.sql`

```sql
create table public.ai_checks (
  id uuid primary key default gen_random_uuid(),
  plan_id uuid not null,
  user_id uuid not null default auth.uid() references auth.users (id) on delete cascade,
  stage smallint not null check (stage between 1 and 5),
  input_hash text not null,
  summary text not null,
  questions text[] not null default '{}',
  action jsonb,            -- {field: 'priority.<key>', value: 'prefer'|'ignore', label}
  tools text[] not null default '{}',
  created_at timestamptz not null default now(),
  foreign key (plan_id, user_id) references public.plans (id, user_id) on delete cascade
);
-- 인덱스 (plan_id, stage, created_at desc), RLS 본인 select/insert/delete, update 없음, anon 권한 회수
```

용량: 점검 1건 약 2KB. 사용자당 하루 최대 30건 → 무시할 수준.

## 작업

1. **마이그레이션 + pgTAP** `ai_checks`(본인 저장·조회, 남의 계획 불가, 수정 불가, anon 불가). `supabase migration up --local` → `supabase test db` → db-types 재생성.
2. **`lib/agent/suggestions.ts`** 단계별 규칙 질문(테스트). 예: 생애최초 → 취득세 감면, 시기 2~3년·미정 → 규제 변경, 기존 대출 → 한도 영향, 3단계 필수 조건 3개 이상 → 후보 감소, 관심 단지 2개 미만 → 비교 안내.
3. **`lib/agent/check.ts`** `runCheck({client, stage, ctx, priorSummaries})`: `runAgent`에 점검용 지시를 덧붙여 실행(`runAgent`에 `systemExtra` 옵션 추가), 마지막 응답의 JSON `{summary, questions, action}`을 zod로 파싱. 파싱 실패면 원문을 summary로, 질문은 규칙 질문. `inputHash()` 순수 함수(테스트).
4. **서버 액션 `runAiCheck(planId, stage)`** (`app/plans/[planId]/_components/ai-check-actions.ts`): 키 확인 → 입력 해시 → 캐시 조회 → 한도 → `runCheck` → `ai_checks` insert. 오류 코드는 M6b와 같음(`rate_limited`, `llm_quota`, `llm_unavailable`). 테스트.
5. **`AssistantPanel`(서버 컴포넌트)** 최신 점검·규칙 질문·채팅 기록을 읽어 `ChatPanel`에 넘김. `ChatPanel`에 점검 버튼, 브리핑, "AI가 확인한 것", 칩, placeholder, 기록 표시. 1~5단계 페이지는 `<ChatPanel planId>` → `<AssistantPanel planId stage>`.
6. **3단계 `?prefill=`** 우선순위 라디오 미리 선택 + "AI 제안 값입니다. 저장해야 반영됩니다" 안내.
7. **리포트**: `createReport`가 같은 입력 해시의 최신 5단계 점검 요약을 narrative로 복사. `generateNarrative`·`narrative.ts`·관련 테스트 삭제, 리포트 화면은 해설이 없으면 "5단계에서 AI 점검을 받으면 리포트에 담깁니다" 링크.
8. **확인**: typecheck·lint·vitest·build·`supabase test db`, 로컬에서 화면 확인(Gemini 키가 있으면 실제 점검 1회).

## 원격 반영

`supabase db push`(20261118000000) → 배포. 그 전에 새 웹을 띄우면 점검 버튼이 `ai_checks` 없음 오류.

## 확인 못 하는 것

로컬 `.env.local`에 `GEMINI_API_KEY`가 없음. 실제 점검 품질(툴 선택, JSON 형식 준수)은 키가 있는 환경에서 확인해야 한다.
