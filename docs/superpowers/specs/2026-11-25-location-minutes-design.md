# 입지 정보: 직선거리 → 소요시간(분) 설계

2026-11-25 · 브레인스토밍 결과

## 왜
4단계 단지 상세와 5단계 비교표의 '입지' 칸이 직선거리(m)만 보여준다. 부동산이 처음인 사용자(이번 타깃)에게 직선거리는 판단 근거가 되지 못한다. "출근 몇 분?", "역·학교·공원까지 걸어서 몇 분?"처럼 그 사람이 실제로 떠올리는 질문에 분 단위로 답해야 한다.

## 목표
- 출퇴근 소요시간을 실제 경로로 보여준다.
  - 2단계에서 대중교통을 체크한 사용자: ODsay 대중교통 시간과 환승 횟수
  - 체크하지 않은 사용자: 카카오모빌리티 자차 시간, 평일 오전 8시 출발 기준
- 역·초등학교·공원까지의 거리를 "약 도보 n분"으로 보여준다.
- 가까운 공원의 이름을 보여준다.

## 하지 않는 것 (이번 범위 밖)
- 배정 학교, 병원·마트, 경사·소음·혐오시설, IC 접근, GTX 같은 호재
- 부부 두 사람의 출퇴근지
- 거래량을 '팔기 쉬움'으로 풀어 보여주기
  - 페르소나 시나리오에서 나온 후보라 다음 차례로 둔다.

## 실패로 보는 경우
- 같은 단지가 화면마다 다른 도보 분으로 보이는 경우
- 다시 열었는데 로딩이 또 도는 경우
- 원격 DB에 경로 결과를 쌓는 경우
- 카카오 REST 키가 브라우저에 노출되는 경우

## 제약
- **원칙 3 예외:** 단지 상세를 열 때 ODsay와 카카오모빌리티를 실시간으로 호출한다. 결과는 원격 DB에 저장하지 않는다. CLAUDE.md 원칙 3에 이 예외를 적는다.
- **무료 한도:**
  - ODsay: 하루 1,000건으로 알려져 있으나 2차 자료다.
  - 카카오: 비상업적 용도는 무료 쿼터 안에서 제휴 없이 사용 가능하다는 답변이 있다.
  - 호출은 상세를 열 때 단지 1곳씩만 한다. 5단계 비교표에서는 아직 저장되지 않은 단지만 호출한다.
- **ODsay 키는 Web 키다.**
  - 등록 도메인: `https://preparations-cyan.vercel.app`, `http://localhost:3000`
  - 브라우저에서 직접 호출하고 `NEXT_PUBLIC_ODSAY_API_KEY`에 둔다.
  - 도메인으로 제한되는 공개용 키라서 원칙 8의 NEXT_PUBLIC 금지에 대한 예외다. CLAUDE.md에 적는다.
  - 2026-11-25 두 Referer 모두 인증 통과를 확인했다.
- **카카오모빌리티 REST 키는 서버 전용이다.**
  - `KAKAO_MOBILITY_REST_KEY`, NEXT_PUBLIC 금지
  - Next 라우트 핸들러를 거쳐 `GET https://apis-navi.kakaomobility.com/v1/future/directions`를 호출한다. 파라미터는 `departure_time=다음 평일 0800`, `summary=true`다.
  - 2026-11-25 실호출로 확인했다.
- 실제 키 값은 `apps/web/.env.local`에만 넣는다. `.env.example`에는 이름만 추가한다. Vercel 환경변수 등록은 사용자가 한다.
- 원칙 9: 외부로 보내는 것은 좌표 두 개뿐이다. 식별 정보는 보내지 않는다. 경로 결과는 LLM에 보내지 않는다.

## 검토한 방식
- **출퇴근 시간**
  - 사용자 저장 시 후보 전체 호출: 한도 초과 → 탈락
  - 주요 업무지구만 미리 배치 계산: 목록 밖 출퇴근지는 표시 불가 → 탈락
  - 직선거리 근사: 대중교통 시간은 환승 때문에 직선거리와 상관이 거의 없어 오해 위험 → 탈락
  - **선택:** 상세 열 때 단지 1곳만 호출하고 sessionStorage에 저장
- **도보 n분**
  - **A. 직선거리 × 우회 계수 ÷ 보행 속도 (선택):** 호출 0, 로딩 0. 4단계 목록, 상세, 5단계 비교표에서 같은 숫자가 나온다.
  - B. 카카오 도보 길찾기 (탈락): 상세마다 호출이 3번 더 생기고 별도 권한 신청이 필요하다. 목록에서는 근사값을 써야 해서 화면마다 숫자가 달라진다.

## 정해진 것
1. **출퇴근 경로 조회**
   - 클라이언트 훅 하나에서 처리한다.
     - 대중교통이면 ODsay `searchPubTransPathT`를 브라우저에서 직접 호출한다.
     - 자차이면 서버 라우트를 호출한다.
   - 화면 표시:
     - 대중교통 `totalTime`분 · 환승 `(버스+지하철 탑승 수 − 1)`회
     - 자차 `duration/60`분 (평일 오전 8시 출발 기준)
2. **캐시**
   - `sessionStorage`에 저장한다. 키는 `mode + 단지 id + 출퇴근지(역 이름 또는 지역 코드)`다.
   - 같은 탭에서는 다시 열거나 새로고침해도 로딩 없이 바로 보여준다.
   - 모든 읽기·쓰기는 try/catch로 감싸고, 저장소를 쓸 수 없으면 매번 호출한다.
3. **실패·한도 초과·출퇴근지 미입력**
   - 실패나 한도 초과 시 "소요시간을 확인하지 못했어요"를 보여준다. 숫자를 지어내지 않는다.
   - 출퇴근지를 입력하지 않았으면 출퇴근 줄을 숨긴다.
4. **좌표**
   - 브라우저에 단지 좌표(경도·위도)와 출퇴근지 좌표가 있어야 한다.
   - 출퇴근지 좌표는 기존 SQL의 `commute_point` 규칙을 그대로 쓴다.
     - 역 이름이면 같은 이름 역들의 중심
     - 지역이면 그 지역 단지들의 중심
5. **도보 분**
   - `ceil(직선거리 × 우회 계수 ÷ 분당 보행 거리)`로 계산하고 "약 도보 n분"으로 표시한다.
   - 순수 함수로 만들어 `lib/calc`에 둔다.
   - 화면 각주에 "직선거리 기반 추정"을 적는다.
6. **공원 이름**
   - `complexes_for_conditions`가 `nearest_park_name`도 돌려주게 마이그레이션한다.
   - 반환 타입이 바뀌므로 drop 후 create한다.
   - 표시는 "○○공원 약 도보 n분"이다.
7. **표시 위치**
   - 4단계 상세 '주변·교통' 탭: 출퇴근 줄, 역·학교 표의 "직선거리" 열 → "도보", 공원 줄
   - 5단계 비교표 '입지' 묶음: 그룹명에서 "(직선거리)"를 빼고 각 줄을 분으로 바꾼다.
   - 4단계 목록 한 줄 요약(`CandidateList`, `livingText`): 도보 분으로 바꾸고 출퇴근 줄은 뺀다.
8. **정렬은 그대로 둔다.** 출퇴근 정렬은 기존 `commute_m`(직선)을 계속 쓴다. 후보 전체를 경로로 조회할 수 없기 때문이다. 화면에서는 직선 m 표시만 없앤다.

## 빌더에게 맡기는 것
- **우회 계수와 보행 속도 값, 그리고 출처를 찾는다.**
  - 2026-11-26 확정: 우회 계수 1.3(Héran 2009, 보행 방해 지역 1.3 이상), 보행속도 1.29m/s(한음 외 2020, 일반인 실측 평균). 사용자가 1.29m/s(B안)를 골랐다.
  - 출처를 확정해 코드 주석과 각주에 적는다. CLAUDE.md "희망 출퇴근 시간: 환산 계수 출처 확인 후" 항목과 같은 값이다.
  - 출처를 못 찾으면 구현 전에 사용자에게 알린다.
- 단지 좌표를 클라이언트에 전달하는 구체적 형태(툴 결과 필드 추가 등)
- 출퇴근지 좌표를 돌려받는 방법(새 RPC나 기존 RPC 반환값 추가)
- 사용자별 하루 경로 호출 상한의 값과 구현 위치
  - 카카오는 서버 라우트에서 막을 수 있다.
  - ODsay는 브라우저 호출이라 클라이언트 쪽 상한만 가능하다.
- 서버 라우트 인증(로그인 사용자만)과 zod 인자 검증: 좌표 범위는 한국
- 카카오 응답의 `result_code !== 0`(경로 없음 등) 처리
